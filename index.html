Platform scope & implementation +

Built one governed platform for enterprise knowledge, document extraction, and AI-assisted workflows, with a modular React interface and secured API and MCP access.

From source to useful answer

React supports Jira, Confluence, documents, and images; the same API serves RAG queries and schema-driven extraction.

Composable for each team

Query, extraction, and ingestion modules are independently enabled, with new sources added through the same structure.

Adaptive extraction uses LangGraph and LangChain to build schema-driven retrieval queries for each requested field. It retrieves relevant chunks from ChromaDB, reranks them by similarity, and constructs an LLM prompt with source material. Results include the field value, supporting context, page number, and model-reported confidence. Subsequent retrieval passes target only unresolved fields, keeping repeated context and unnecessary model input down.

The platform follows a vertical slice architecture: query, adaptive extraction, Jira, Confluence, and other modules can be switched off through feature flags or removed independently. New ingestion sources can be added without reshaping the rest of the system. The API supports Kerberos authentication, while the MCP provides group-authorised access through time-limited JWT API keys for Claude Code and Copilot CLI.

Portfolio-wide delivery

Application portfolio modernisation

Delivered at scale
01Inherited

A large portfolio combined Windows-hosted services with inconsistent release paths across .NET, React microfrontends, and NestJS APIs.

02Reshaped

Established a repeatable migration path covering runtime upgrades, code and GitLab CI remediation, containerisation, and Rancher configuration.

03Running

Applications now follow a consistent Kubernetes delivery model on Rancher, reducing Windows server dependency and making migrations repeatable.

Portfolio migration approach +

Work began by assessing each application’s runtime, build, and release constraints. .NET Core 3.1 services were upgraded to .NET 6 or .NET 8, while React microfrontends and NestJS APIs were adapted for container delivery. The in-house GitLab CI templates were introduced and failures across builds, tests, SonarQube, Nexus IQ, container creation, application configuration, and Rancher deployment were resolved application by application. This established one reusable delivery approach instead of a series of isolated migrations.

Messaging service migrations

Running in production
01Inherited

AutoSys-scheduled .NET console processes tied to Windows servers.

02Reshaped

Introduced a Solace bridge, long-running subscribers, AutoSys batch changes, and end-to-end testing.

03Running

Kubernetes production migrations with no post-deployment defects.

Messaging migration details +

Because AutoSys was not available in Rancher, a .NET bridge remained on Windows to receive command arguments from AutoSys jobs, construct messages, and publish them to Solace queues. Each former console process became a long-running Kubernetes subscriber using the in-house library built on the official Solace .NET packages. The migration covered application restructuring, message handling, AutoSys batch changes, end-to-end testing, and production release.

06

Financial API performance optimisation

Performance improved
01Inherited

Financial APIs under high memory pressure with multi-minute responses.

02Reshaped

Moved filtering and distinct work into SQL Server, avoided large intermediate lists, and loaded only the related data each endpoint needed.

03Running

Lower memory usage and materially faster endpoint responses.

Query & processing changes +

The APIs were loading large result sets and performing filtering and distinct operations in memory. The LINQ and processing flow was redesigned so SQL Server handled that work before returning results, large intermediate lists were avoided, and related data was loaded only when an endpoint needed it. This reduced memory pressure and removed the multi-minute response bottleneck.

Informatica to Python/Prefect

Internal plugin
Migration path established
01Inherited

Legacy Informatica workflows requiring manual discovery and migration analysis.

02Reshaped

Built stateful discovery, assessment, reporting, and Python and Prefect code generation.

03Running

A stateful path from legacy workflow evidence to assessed and generated Python/Prefect implementations.

Migration workflow details +

The plugin separates discovery, assessment and code generation into focused skills. Discovery accepts manual evidence or Informatica XML exports and records missing behaviour and unresolved references. Assessment examines complexity and commonality across workflows. Generated code follows the firm’s Python project structure and AutoSys, Rancher and Prefect conventions. Each skill’s progress is tracked in JSON so the process can continue across runs.

The discovery step keeps extracted metadata, assumptions and missing runtime details explicit. Parameter files, scheduler details, production run history and SME notes provide additional context when available for downstream assessment and code generation.
